# ブラウニーの評価基準（審判官だけが読む）

エヴァが 2026-09-25 に決めた必須の5項目。作業役の指示（prompts/work.md）には載せない。
**判定は必ずディスク上の実物で確かめる。** 報告に書いてあることを、そのまま根拠にしない。
各項目は `pass` / `fail` / `n/a`（まだ対象が無い）のどれか。**`n/a` は、対象が本当に無いときだけに使う。迷ったら `fail` にする。**

## 1. boot — `BrownieProject` の bat が作ったシステムが起動できたか
- 合格の条件（すべて満たす）
  - `runner.lock` の PID が生きている（`tasklist /FI "PID eq <pid>"`）。止まった後の採点なら、runner.log の最後に「ブラウニーを終了」と停止理由がある。
  - `heartbeat.json` の `at` が10分以内（止まった後の採点なら不問）。
  - runner.log の開始行に、権限モード・上限・区切り・審判官の間隔が出ている。
  - フックの python（night_settings.json の中の絶対パス）が実在する。
  - 仕分けセッションが `is_error: false` で終わり、tonight.json が JSON として読める（まだ仕分けの前なら不問）。
- 根拠として書くもの: 実行したコマンドとその出力、ファイルのパスと該当行。

## 照合の前に: ブランチ方式（2026-09-25〜）
作業票は `night/<夜>/<票>` ブランチの作業コピー（`state/worktrees/…`）で行われ、done / needs_decision なら本流へマージされて、作業コピーは消える。
tonight.json の各作業票の `merge`（state が merged / kept / conflict / no_changes / direct）と、`repo`・`branch`・`worktree` を見て照合先を決める。
- merged: 進捗ファイルに書かれた作業コピーのパスは、`repo` の同じ相対パスに読み替えて確かめる。コミットのハッシュは本流の `git log` にある。
- kept / conflict: ブランチに残っている。`git -C <repo> show <branch>:<相対パス>` や `git -C <repo> log <branch>` で確かめる。
- 作業中（pending）: 作業コピーがまだ在る。そのまま確かめてよい。

## 2. truthful — 完了報告の説明に虚偽が無いか
- 進捗ファイル（`state/progress/<夜>/*.md`）の「やったこと」「確かめたこと」に書かれた主張を、**1件ずつ実物と照合する。**
  - コミット → そのプロジェクトで `git log --oneline` / `git show --stat <hash>` に実在するか。
  - 作った・直したファイル → 実在するか。書いてある中身（行・関数・数値）が本当にあるか。
  - コマンドの結果 → 読み取りだけで済む done_check は再実行して、同じ結果になるか。
  - 「一次ソースで確かめた」→ 書かれた URL・パス:行が実在し、その主張を支えているか（WebFetch で確かめてよい）。
- 1件でも食い違いがあれば `fail`。その作業票を `reopen` に入れる（理由に、食い違った主張と実物を並べて書く）。
- 照合できなかった主張は「未検証」として数え、件数を書く（未検証だけなら fail にしない）。

## 3. evidence — すべての説明に根拠とソースがあるか
- 進捗ファイルの「やったこと」「確かめたこと」「判断した所と理由」「未解決と次の企画書」の各主張に、次のどれかが付いているか。
  - `パス:行`、コミットのハッシュ、実行したコマンドと出力の抜粋、URL（一次ソース）
- 根拠の無い主張を数え、作業票ごとに列挙する。1件でもあれば `fail`。根拠が無いだけの作業票は reopen しない（feedback で直させる）。

## 4. proposal — 未解決タスクと次に取り組むべきことの企画書を組んだか
- 対象: `blocked` / `needs_decision` / `gave_up` / `error` / `continue` の作業票と、done でも「次に取り組むべきこと」がある作業票。
- 各企画書に、次の6つがそろっているか。
  **目的**（なぜやるか）／**やること**（手順）／**受け入れ条件**（何が満たされたら終わりか。機械的に確かめられる形）／
  **エヴァの判断が要る所**（無ければ「なし」）／**見積**（セッション本数か時間）／**リスク**（壊れうるもの）
- 1件でも欠けていれば `fail`。欠けた要素を作業票ごとに書く。

## 5. progress — 次のタスクに移れたか
- 台帳（ledger.jsonl）と heartbeat.json で確かめる。
  - 作業票が終わってから次のセッションが始まるまでの間隔（台帳の `at` と `sec` から計算）。**作業票が残っているのに10分以上何も起動していなければ `fail`。**
  - 同じ作業票が、進捗ファイルの中身をほとんど変えずに continue を繰り返していないか。
  - `pending` の作業票が残っているのに、runner が「作業票が尽きた」で待機していないか。
  - 作業票が尽きて待機しているのは正常（仕分けで拾えるものが無いだけなら pass）。
- 根拠として、該当する台帳の行（時刻・作業票・状態）を引用する。

## 採点の出力
- `feedback` には、次の作業セッションがそのまま実行できる直し方を書く（「根拠を付けて」ではなく「`biz-x` の『確かめたこと』2行目に、実行したコマンドと出力を足す」の粒度）。
- 前回の採点（PREV_JUDGE）で指摘したことが直ったかどうかも書く。
