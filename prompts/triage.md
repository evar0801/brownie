## 分類
- **run**: 無人で完了まで行ける。**完了判定が機械的に確かめられる**（コマンドの終了コード・ファイルの有無・grep の一致など）。
  不可逆操作（push・公開・配備・実サーバーの起動停止・課金・送信・凍結ワールドへの書き込み・恒久削除）を含まない。
- **decide**: エヴァの判断が要る。**2026-09-25〜、ブラウニーは decide も推奨案で実装まで進め、自動でマージする（朝にエヴァが残すか revert で戻すかを選ぶ）。** だから decide にも、推奨案を実装したときの機械的な完了判定を `done_check` に書く（例外: 実装が禁じられたプロジェクトは「DECISIONS.md に選択肢を追記済み」）。
  以下は従来の説明: 夜のうちに一次情報で調べて選択肢 A/B/C（各案で何ができて何ができなくなるか・推奨）を用意すれば、朝の決裁が一言で済むもの。
  **ただし**、`NIGHT_NO_MERGE_PROJECTS` に挙げたプロジェクトの票は、司令塔が合流させない（ブランチに作るまでで、朝の報告の「保留」に載る）。ほかのゲームのプロジェクトの decide は、今までどおり推奨案で実装して合流する（2026-09-25 エヴァの決裁）。
- 上のどちらにも当たらないものは作業票に入れず、`skipped` に理由を1行で残す。

曖昧なものは run にしない（受け入れ条件が書けないなら decide）。件数は絞らない。

**run にしてよいのは wide だけ**（独立していて、機械で完了を判定できる）。理解と判断が分けられない deep（設計・原因不明のバグ・曖昧な要望）は decide にする。
run の作業票は**契約5項目**（`files`=担当ファイル／`inputs`=入力／`goal`=出力／`read_scope`=読み範囲／`done_check`=完了判定）が全部埋まること。
1つでも空なら分解が終わっていない＝run にせず decide にする。読み範囲は担当ファイルから演繹できないので、必読と凍結を別に書く。
**完了した項目の片付けは作業役がやる。** run が done になったら、作業役がその項目を PENDING（または HANDOFF の「次の一手」）から抜き、プロジェクトの作法どおり DECISIONS へ1行で移す。
だから、出典の PENDING.md・DECISIONS.md は `files` に入れ、`read_scope` の凍結には書かない（凍結にすると誰も片付けず、同じ項目が PENDING に残り続ける。2026-09-25 砂場で実測）。「司令塔が移す」とは書かない（司令塔にその処理は無い）。
作業票の files に、その票のプロジェクトの外のパスを入れない（ルートの DECISIONS.md も入れない）。
同じファイルを担当する run が2枚できたら、1枚にまとめる（同じ塊を別セッションが書くと統合できない）。

## 出力
`{TONIGHT}` に次の JSON を書く（UTF-8）:
```json
{"tickets": [{"id": "英小文字とハイフンの短い識別子", "project_dir": "絶対パス", "title": "日本語で1行",
  "source": "パス:行", "kind": "run|decide", "goal": "何が満たされたら達成か",
  "files": ["担当ファイル（書いてよいもの）"], "inputs": "入力（元になる文書・データ）", "read_scope": "必読: …／凍結: …", "done_check": "機械的な確かめ方（decide も推奨案を実装したときの判定。実装が禁じられたプロジェクトだけ「DECISIONS.md に選択肢を追記済み」）",
  "effort": "low|medium|high", "priority": 1, "why": "選んだ理由を1行"}],
 "skipped": [{"source": "パス:行", "title": "…", "reason": "…"}]}
```
effort の目安: 定型の置換・整形＝low／実装・修正＝medium／設計判断・難しいデバッグ・decide＝high。
priority: inbox＝1、期日が近いもの・他の作業を塞いでいるもの＝2、それ以外＝3。

書き終えたら「OK run=n decide=m skipped=k」とだけ返して終了してください。
